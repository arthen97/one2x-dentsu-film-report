日本 Personal Agent 场景深度战略研究

2026-10-20 · 决策对象：Iris 在日本的首发场景、MVP 范围、取胜方式、能力建设与 90 天验证 · 约 2.3 万字（含表格），通读约 45 分钟；只看 §0 约 3 分钟。

0结论

一句话：在日本以"替用户执行"取胜。首发以机酒与在日居民餐饮（预約困難店、多人聚餐两个小切口）为 P0（U25）；发现页为与对话并列的主线模块（U26）；MVP 同时带上邮箱观察项和一组勾子（含跨境游客餐饮），先验证用户愿不愿意把事交出去。

Iris 在日本有本地渠道、企业背书和本土合规，但多数生活任务已被成熟平台覆盖。本报告回答一个问题：在哪些任务里，这些资产能变成用户感知得到的增量和可收费的商户权益。

用户心智与收费

  • 用户心智：替你省钱、省事、体验更好生活。省钱：机酒盯价、降价重订、闲置订阅；省事：聚餐协调、改约取消、邮箱跟进、行程变动；体验更好生活：预約困難店、演唱会与限量品抽选，Iris 替你守着、替你报上，拿不到时说明停在哪一步，不承诺结果（§5.1 原则 7）。每个任务结束时给出前后对照和回执。
  • 收费：短期只收低价用户订阅、不向商户收费、接受可控补贴（U21）；短中期按结果收费（成交抽佣、节省分成）；长期只向商户抽佣、用户免费；联盟分成在任何阶段都不可用（S02、S30，§6）。

核心发现

以下均为本文判断，证据等级见附录 A。

  1. 差异化在执行层，不在推荐层。 推荐已被食べログ、価格.com、Google Maps 占满；能打电话、持续盯价并锁单、订完后替用户跟进变化，才是用户感知得到的增量（S31、D02）。
  2. 用户能看见前后对照的任务更早成立。 省了多少、退回多少、订没订到，用户能自己判断，也才能按结果收费；机酒盯价和取消闲置订阅都属此类（U04）。
  3. 在日居民的普通餐厅预约没有增量。 本地人一两分钟就能订到；值得做的只有预約困難店和幹事式聚餐协调两个小切口（U12、D05）。
  4. 跨境游客餐饮增量最高，但只做日本时是低频交易。 记忆、主动性和本地渠道都发挥不出来；因为故事好讲，先以勾子形态进 MVP，完整接入排第二梯队末位（U14、U15、U20）。
  5. P0 为机酒加在日居民餐饮，按周发生的入口仍待验证。 机酒一年几次；餐饮两个小切口按事件与按月发生，是记忆与常设规则最能发挥的场景，所以升为 P0（U25）；订完后的航班变动跟进能多几个接触点；但都补不上按周发生的需求，所以把邮箱持续跟进列为 90 天观察项（D05）；发现页由观察项升为与对话并列的主线模块（U23、U26），按记忆、邮箱、日历与收藏推测用户想做、需要什么，给出信息、想法或备好的任务，引发交办的比例设门槛；现有平台看不到这些私人上下文，只能按兴趣推荐（§2.2）。
  6. 两条硬约束不随伙伴背书消失。 医疗、税务、资金执行受专业资格限制，只能汇总、预填与协调；夜间娱乐、婚恋、含酒精餐饮有年龄门槛，产品必须掌握用户年龄（S11、S23、S41、S24）。

2市场约束与竞争格局本文判断

先说结论六条约束决定首发只能落在"有执行增量、有直接商户关系、不碰专业资格"的交易场景；现有玩家分别占住了推荐、电话执行和生态入口，没有一家同时做到跨平台执行、持续责任与个人上下文。

2.1六条约束

约束一：库存碎片化，执行要走三条路径。 平台公开 API 只给查询、不给预约写入（S31）；聚合平台对外部 Agent 封闭，只能走官方深链；独立站（名店、温泉旅馆、品牌与沙龙官网）可由云端电脑直接操作。高端餐厅集中在 TableCheck 与 OMAKASE，大量独立餐厅只接电话（D02、P07）。结论：执行层要同时支持 API、官方深链和 AI 电话，电话是日本特有的差异化（D01）。

约束二：平台收费模式排斥私密 Agent 媒介。 食べログ按到店人数向商户收费（S03），HOT PEPPER 限制向餐厅收取对价的网站使用其服务（S30），楽天联盟禁止私密消息与自动工具（S02）。结论：联盟变现不可用，收入只能来自用户付费、直接商户合同或机构采购。

约束三：专业资格与牌照边界。 保险诊疗禁止患者介绍对价（S11），税务文书限于税理士（S23），资金执行与投资业务各有注册框架（S08、S27），个人信息跨境提供有法定路径（S36）。结论：医疗、税务、资金执行、介护只能做协调，不能抽佣，不能自主执行资金。

约束四：请求不等于成立，责任要有归属。 请求预约要餐厅接受才成立（S04），健诊仮预约后要等邮件确认（S19），車検从估价到到店分两步（S20）。结论：回执必须区分"已提交"和"已成立"，人工兜底成本进入单位经济（§6.2）。

约束五：身份与年龄是硬门槛。 夜间娱乐有法定年龄限制（S41，需复核具体条文），婚恋平台要求 18 岁以上并做本人确认（S24），应用商店限制促成性服务（S42，需复核具体条款）。结论：产品必须掌握用户年龄，年龄敏感场景启用前做身份验证（§7.2），性風俗関連特殊営業不进入产品范围。

约束六：用户已有工具足够好。 Google Maps、食べログ、PayPay（S07）、各 OTA 已覆盖一键能完成的任务。结论：只有多约束协调、跨语言、持续盯价、跨平台抽选这类用户自己做不好的任务才值得针对性投入；店铺筛选交给通用能力操作 Google Maps（U03、U05）。

2.2竞争格局

聚焦三股有张力的力：替代品（现有平台与 Agent）、买方（用户已有工具）、供应商（商户与库存系统）。

结论：推荐层已饱和，执行层被 AutoReserve 占了电话、被 TableCheck 占了结构化库存，生态入口被 Rakuten 与 LINEヤフー占住。留给 Iris 的位置是"跨平台执行＋持续责任＋个人上下文"的组合，跨语言是跨境场景的附加能力。这也是"赢的目标"的依据：真正值得抢的不是第 N 个 AI 餐厅搜索，而是用户默认授权的执行层（D02）。

推荐层饱和，不等于发现需求不存在。有目的的检索在 Google Maps 与食べログ；闲逛种草在 Instagram 与 TikTok，日本 Z 世代找店最常用 Instagram（S122）；按时间、地点与场合推荐一家店的 AI 有 ぐるなび 的 UMAME!（S123）。它们看不到用户的邮箱、日历与行程，只能按兴趣推荐。Iris 从这些私人上下文推测用户想做、需要什么，再把事办成，这是发现页作为主线模块的依据（§4.3、§5.1 原则 9、U26）；不做找店检索，店铺筛选仍归通用能力（J14）。

3在哪里竞争：场景树

3.1拆分原则

先说结论用 JTBD 定义单元，一行一条任务，写成"在什么情境下，用户想完成什么，以得到什么结果"；发生在不同时点或依赖不同能力的任务不合并；一级按"是否发生商户交易、是否受专业资格约束"切，二级按行业切，客群（跨境游客／在日居民）作横切维度。

一级四类互斥且覆盖全部候选：A 消费交易（找、订、付、售后，Iris 可执行并可从商户侧收费）；B 关系与社交（无商户交易，价值在用户侧）；C 生活事务（无交易或交易由用户自助完成，Iris 做提醒与代填）；D 受监管专业服务（执行受资格限制，只能协调）。

二级在 A 下按行业分，因为执行路径、商户类型、变现方式随行业变化。

分层的含义：通用 Agent 能力（云端电脑的网页操作、AI 电话）是底座，任何官方网站与商户都可按用户授权尝试完成任务；场景树与优先级回答的是"哪些场景值得针对性投入"，不回答"能不能做"。未获针对性投入的场景仍由通用能力承接（U05）。跨境游客的行程成形与紧急求助属于横切任务，由通用能力与电话承接，不单列场景。

归并规则：共享同一笔订单的任务（优惠券、积分、送礼、物流）并入所属交易，作为触发或配套环节；共享同一支付动作的任务（缴费、账单、NHK、积分到期、记账）合并为 C1；受同一牌照约束的任务（移动支付、转账、资产执行）合并为 D3；预约按是否受医疗资格约束拆入 A1、A5、D1。

3.2场景树

一行一条任务（J 编号）。同一个二级场景里，发生在不同时点、依赖不同能力的任务分开写：跨境游客"订到店"靠电话与回电接听，"到店点对菜"靠扫码菜单，是两条任务；机酒的"一次比价"与"持续盯价"也是两条。表 5-1 的 Aha 与 D04 的能力都按 J 编号对应。投入列只表示针对性投入级别（§4.3），不表示能否完成。

MECE 检验：伙伴候选清单（P06）的每一项恰好进入一个二级场景；每条 J 只属于一个二级场景，J10 的渠道权益由机酒与餐饮共用，归 A2 管理。A4 为团队补充（U03），外卖、游客行程与紧急求助为本文补充，归入 A1、A2 或横切。一级之间以"有无商户交易"和"有无专业资格约束"两个二值条件划分，不存在同时属于两类的任务。

3.3对照竞品已验证场景的取舍

先说结论竞品用户研究里被验证的十类场景（D05），只有"旅行后勤与异常跟进"值得新增为任务，并入机酒主线；"承诺与事务持续跟进"已是 90 天观察项，补上闲置订阅解约作为第一个具体任务；其余或已覆盖，或在日本缺少对应需求与变现，不新增。按节省分成倒推、缺少用户痛点依据的候选不纳入（U13）。取舍标准是能否对产品设计或市场推广产生真实价值，场景并非越多越好。

不纳入的两项：通信与电力套餐优化，伙伴清单的原意是账单提醒与异常涨价预警（P06），切换一年最多一次，还要运营商与电力代理店合同，C1 的针对性投入因此放在闲置订阅解约；保险理赔没有任何输入来源，退税归通用覆盖（§5.12）。

4在哪里竞争：优先级

先说结论先评"这件事交给 agent 做，agent 相对现成工具有没有优势"，用七个维度逐一评，再分层。结果：P0 为机酒，加在日居民餐饮的预約困難店与多人聚餐协调两个小切口（U12、U25）；跨境游客餐饮完整接入排第二梯队末位，先以勾子形态进 MVP（U14、U15、U20）；高频入口空缺，邮箱跟进列为 90 天观察项。MVP 范围见 §4.3。

4.1评估框架：agent 做这件事的优劣势

一个 agent 相对平台与工具，只多出四样东西：替用户跨平台、跨语言执行；跨时段持续负责；积累用户上下文并主动行动；把 Iris 的本地资产变成用户权益。一个场景若让其中大部分发挥不出来，即便用户痛点很强、交易增量很高，它也只是一次性交易产品，不是 agent 的切入场景。七个维度分三组：前四个看 agent 的优势能否发挥（执行增量–资产兑现），两个看能否形成信任与收入（可核验–变现），一个是门槛（可控）。

评分为高、中、低三档序数，不加权求和。分层规则：

  • 先拆任务再评：同一场景里用户自己做的成本差别很大的任务分开评；执行增量为低的直接归通用覆盖。
  • 优先切入（P0）：执行增量至少中高，且频次、上下文、资产兑现至少两项为高、可控不为低。目前没有场景满足，高频入口空缺；美容三项全高，但执行增量只有中，用户在现有平台上自己就能约，所以不进 P0（U19）。
  • 价值证明（P0）：执行增量与可核验都高，服务在日居民、上下文可得，让用户和商户看见钱。
  • 第二梯队（P1）：未进 P0、变现不为低；内部按新增投入排序，复用已建能力越多、新签约与新能力越少的越先接。
  • 勾子（P1）：变现为低、只展示一种能力；随 MVP 上线，由通用能力（云端电脑与浏览器操作、AI 电话）跑通即可，不做针对性优化。
  • 配套（P1）：不单独构成用户任务，依附主线或商户合作。
  • 通用覆盖（P2）：执行增量低，或可控为低，由通用能力承接。

被评对象是表 3-1 中有针对性投入候选的 11 个场景；P2 不逐项评（§4.3）。

4.2评估总表

七个维度的关键判断：

  • 执行增量：只有用户自己做不到或不想做的事才算；一次性比价、筛选和一两个人的餐厅预约，现成工具和本地人自己已做好（U12）。
  • 频次：跨境游客一年一次、两周就走（U14）；在日居民餐饮按周月复发，但多数预约无增量；美容按 4 至 8 周复发；机酒与抽选事件驱动，但任务跨时段。
  • 上下文：游客的行程、社交、发现分别在携程、微信、小红书，都接不到；居民的预约、订单、账单都在 Gmail 与 LINE 里（D04）。
  • 资产兑现：对居民，渠道、背书、合规都能变成获客与权益；对游客只有商户签约一端有用（U14）。
  • 可核验与变现：多人聚餐协调最难让用户看见效果；联盟变现不可用（S02、S30）；可控是门槛。

"日本 Top 1 竞品"列写的是日本用户今天完成这件事最常用的产品，多数不是 agent，而是传统互联网产品；规模数字的性质分别标为调查官方厂商，没有可靠排名数据的写明未核实。

4.3综合结论

总表读法：

  • 在日居民餐饮预约拆开后，只有两个小切口有增量。 一两个人订一家店，本地人一两分钟就能完成，按 §8.3 的门槛也不可能再降 30% 投入时间，所以归通用覆盖（U12）。预約困難店的反复拨打、盯放位与抽选，以及幹事式的多人聚餐协调，才是本地人真正花力气的地方。本报告原判断前者小众、后者按月发生且正面对上 ぐるなび Sync Vibes（D02），作第二梯队；2026-10-21 产品决定升为 P0 主线，理由是餐饮高频、是记忆与常设规则最能发挥的场景（U25）；投入深度仍为轻量接入，原判断保留为 §8.4 的切换条件（再委托率不高于普通预约则退为通用覆盖）。
  • A2 机票酒店比价与盯价是唯一执行增量、可核验全高且上下文高的场景，是 P0 唯一的主线：盯价是 agent 原生的持续责任，差价以日元可见，确认邮件就在 Gmail 里。它有两个短板：可控，即自动下单的赔付与旅行业法，所以首次必须确认、先做免费取消价位；频次，出行年数次，无法单独养成习惯。订完之后的航班变动、改签退款、值机与积分到期跟进（J31）并入主线，是竞品已验证的旅行后勤任务（D05），让一次出行有多个接触点，部分补上频次短板。
  • 跨境游客餐饮：增量最高，但不是同一批用户。 执行增量与可核验都高、有商户侧变现，所以留在第二梯队（U09）；但频次、上下文为低，资产兑现只有商户一端，只做日本时记忆与主动性没有回报（U14）。完整接入排末位，因为要为一次性用户新建中国入口、微信通知、PIPL 合规与国区备案（D04 2.3、U15）。故事好讲、传播性强，所以先以勾子形态进 MVP：通用能力跑通 H13 日语电话与回电接听、H14 拍菜单点单，经合作酒店免安装触达，考核完成率、首次价值与传播效果，不考核留存（U20）。做全球旅游市场时再按频次、上下文重评。
  • 美容沙龙复约（A5）的 agent 属性强于线上购物（A3）：频次、上下文、资产兑现三项全高，但执行增量只有中，用户在现有平台上自己就能约，按 §4.1 的门槛不进 P0（U19）；排在两个餐饮小切口之后、线上购物之前。
  • 按周发生的入口仍待验证，列观察项而不硬补。 机酒一年几次，餐饮两个小切口按事件与按月发生，都不是按周发生的任务。竞品研究里重复潜力最高的是承诺与事务的持续跟进（D05），对应在日居民邮箱里的订单、账单、订阅与预约确认（J23、J24、H5、H6）。日本本地缺少证据，90 天内只看连接邮箱的用户中提醒被采纳和主动追问的比例（§8.2、§8.4）。其中闲置订阅有本地数据：50.5% 遇到过首月免费后被自动扣费，19.1% 有忘了取消的订阅（S64）。发现页（U23）原列第二个候选，2026-10-26 产品决定升为与对话并列的主线模块（U26）：按记忆、邮箱、日历与用户分享的收藏，猜用户想做、需要什么，给出信息、想法或备好的任务，用户自己打开、不推送；90 天内看发现页引发交办的比例、每周打开率与推测被否定的比例，设门槛（§8.2、§8.3）。基于泛兴趣的信息与种草在机酒过 §8.3 门槛后再做，因为最容易变成噪音（D05、S124）。
  • 勾子与第二梯队的分界是变现：抽选、夜间娱乐、婚恋的执行增量也高，但变现为低，只展示一种能力，不计营收，预算按传播效果评价；跨境餐饮有商户侧变现，所以进第二梯队而不是勾子。闲置订阅解约同理：结果以日元可见、传播性强，但单个用户每月只省几百到一千日元，商户也不会为解约付费（S64），所以是勾子。

分层含义与 §4.1 一致：P0 针对性建设专用接入、商户合作与责任设计，验证商业闭环；P1 轻量针对性接入；P2 不做针对性投入，由通用能力承接。

  • P0 价值证明：A2 机票酒店比价与盯价。 含订完之后的行程变动与售后跟进（J31）；90 天内先限定在免费取消价位、首次确认的范围内验证用户价值。
  • P0 主线还包括 A1 预約困難店盯位与抽选、A1 多人聚餐协调（U25）。 两个餐饮小切口共用电话、名店接入与 LINE 能力，90 天内与机酒并行小规模试点；投入深度为轻量接入。
  • P1 第二梯队（按新增投入排序）：A5 美容沙龙预约与复约、A3 线上购物选型与比价、A1 餐饮预约与点餐·跨境游客。 在机酒通过 §8.3 用户价值门槛后接入；跨境餐饮的完整接入排末位，因为旅游低频（U15），但先以勾子形态进 MVP（U20）。
  • P1 勾子（传播叙事，不计营收）：A6 演唱会与限量品抽选、A5 美容优惠、A5 夜间娱乐电话预约、B1 婚恋网站资料代填、C1 闲置订阅发现与解约（兼作邮箱持续跟进观察项）。 随 MVP 上线，由通用能力（云端电脑与浏览器操作、AI 电话）跑通即可，不做针对性优化。
  • P1 配套（随主线建设）：A1 的改约取消与截止提醒（J05）、常去店与同行者记忆（J06），随任何预约任务出现；A4 门店内选品推荐、A3 中的优惠券／积分／送礼触发／物流；C1 账单缴费提醒，兼作 90 天观察项。
  • P2 通用覆盖：A1 一两个人的普通餐厅预约、A4 店铺筛选、A5 車検、B2 情绪陪伴、C2 行政搬家、C3 退税、报销与资产事务。 不逐项评：执行增量低（现成工具足够或本人到场不可替代），由通用能力承接；出现具体买方或伙伴时升为 P1。
  • MVP 范围： MVP 是 P0 加若干 P1：机酒，两个餐饮小切口，发现页主线模块（U26），邮箱观察项（含闲置订阅解约），勾子，以勾子形态上线的跨境游客餐饮，配套随预约任务出现；美容复约、线上购物比价与跨境餐饮的完整接入在机酒通过 §8.3 用户价值门槛后进行（U19）。
  • P2 法规限定：D1 医疗预约、D2 用药与介护、D3 资金执行。可控为低，只做汇总、预填与协调，本人提交；健诊在出现机构买方时走机构路径升为 P1。

5如何取胜：Aha 时刻与价值主张

先说结论取胜靠两件事。一是让用户登录后，在首次对话 120 秒内经历第一个 Aha，并用每个 Aha 换下一层授权；二是每条主线的价值主张都有明确的客群、替代对象与差异化。场景卡字段固定：客群与任务、替代对象、差异化、Aha、执行路径、变现与伙伴权益、获客勾子、待验证假设、风险、90 天指标。各场景的聚合平台、独立站、预订系统与电话路径名单，以及 agent benchmark 的基准任务，见 D04 第 2.4 节；本文的执行路径只写类型。

5.1Aha 时刻与授权阶梯

Aha 是用户第一次明显感到"Iris 解决了一件重要、而且我原来很难解决的事"的时刻（D03 称首次有意义价值时间）。它决定用户是否给出下一层授权，所以 Aha 的顺序就是授权的顺序，也是产品建设的顺序。表 5-1 按建设顺序排列，每个 Aha 写明真实情境、用户看到的回执，以及之后只问的那一句话。设计依据是场景调研（U03、U07）与日本本地的官方规则、调查、媒体和用户自述；竞品用户声音（D05）作参考。十一条原则：

  1. 在精不在多。 Aha 在精不在多：每个场景 1 至 2 个，P0 主线 4 个。只收同时满足三点的时刻：用户自己做不到或做起来很费力的事被办成了；结果肉眼可见，即订到了、省下或拿回了日元；之后能自然换来下一层授权。功能细节、防错规则与合规要求写进执行要求，不算 Aha（U18）。
  2. 第一个 Aha 只需登录。 不做免登录：用户先以 Google、Apple 或 LINE 登录，Gmail 是用户上下文的主路径，跨境游客同样经 Gmail（U22）。第一个 Aha 在首次对话 120 秒内发生：在日居民是 H1 机酒比价卡片；跨境游客是 H13 日语电话。注册时不连 Gmail，在第一个需要邮件的任务里请求；不用 Gmail 的用户经每人一个转发地址覆盖（U27）。待定：120 秒从登录完成还是从连接 Gmail 起算。
  3. 回执可核验。 每个 Aha 有可核验回执（预约编号、商家回复、通话摘要），回执区分"已查到、已申请、已确认、还需你做"四种状态，不把"查到有位"说成"已订好"；完成定义不清是竞品用户反馈里最常见的失败（D05）。
  4. 不依赖平台 API。 首发的 Aha 不依赖平台 API。
  5. 每次只问一句。 每个 Aha 之后只问一个问题，用它换下一层授权；同一任务内的授权按动作递进：盯价先通知并一键确认，首次确认后才开放限额内自动锁定，而且只锁可免费取消的价位（H2）。
  6. 授权按动作分。 授权按动作分，不按场景分：盯价、盯放位、当落这类重复查询授权一次持续有效；付款、发消息、对外承诺每次出卡片或在限额内自动（§7.3）。用户确认过一次同类任务后，可以把它设为常设规则，写明条件、限额与只订可免费取消的，例如"连休前比好机酒，限额 5 万日元"；之后 Iris 在规则内直接办、事后给回执，规则随时可暂停或取消（U23）。需要新权限、持续盯守或推送的后续动作（写入日历与出发提醒、跟到当天、盯到免费取消截止、下月核验）不默认做：首次在回执里给选项、之后同类自动、设置里可关，不占 Aha 之后的那一句（U26）。竞品用户既因频繁审批放弃任务，也因未经确认发送而收回授权（D05）。
  7. 做不到也要有 Aha。 做不到也要有 Aha：说明停在哪一步、保留可接手状态、给替代（H8）。同一类任务在不同商户结果不同，不承诺"都能自动完成"（D05）。
  8. 跨时段的第二次。 P0 与每个第二梯队场景至少一个跨时段的 Aha（机酒 H3、H4，预約困難店 H7，聚餐 H10，美容 H11，邮箱观察项 H6，配套 H15）：首次 Aha 靠新鲜感，留存靠下一次真实需求出现时 Iris 记得上次、少让用户重复解释（D05）。
  9. 主动的边界。 主动联系用户（推送、在对话里开口）只针对用户已交办、或邮箱里已存在的事：变化、到期、截止；已交办包括用户确认过的常设规则（原则 6）。用户自己打开的发现页可以给信息与想法，但每张卡写明推测依据，不推送，不卖排序，不在其中请求授权（U23）。不推销商品：发现页里的店铺与活动只来自用户自己的上下文，商户不能付费换位置；优惠类 Aha（H18）须用户先开启。竞品用户对不需要的商品推荐明确反感（D05）；Muse 的建议被评测者认为在诱导用户交出更多个人数据（S124）。
  10. 勾子与 P2。 勾子的 Aha，以及以勾子形态进 MVP 的跨境游客餐饮（H13、H14），随 MVP 上线，由通用能力（云端电脑与浏览器操作、AI 电话）跑通即可，不做针对性优化。P2 场景不设计专门 Aha：普通餐厅预约、退税、健诊、游客落地行程与紧急求助由通用能力完成，照常给回执。机酒与餐饮的渠道礼遇（J10）不单列 Aha，伙伴权益登记后在回执中标明。
  11. 电话的礼仪。 电话类 Aha 一律开场披露 AI 身份与委托人，只在店方营业或开放窗口内拨打，重拨有上限；店方表示拒绝后标为"仅本人致电"，不再拨打。已有店主公开抱怨 AI 订位电话反复来电（S88、S121）。

5.2A1 餐饮·跨境游客（第二梯队末位）

6商业模式与单位经济

6.1谁付钱：按阶段演进

先说结论收费分三个阶段。短期靠用户订阅，因为商户权益与结果归因都还没建立；短中期加入按结果收费，用可见的差价或成交向用户或商户收取；长期只向商户抽佣，用户免费。每个阶段的切换由可核验的条件触发，不按日历推进。

各模式的证据与冲突：

模式 有效证据 核心冲突 阶段
用户订阅／按任务服务费 真实支付与续费（S09） 与免费平台比较；低频任务不适合月订阅 短期主力，短中期保留
商户接入与持续运营费 接入验收、监测、异常处理的合同与付款 单店实施成本；收费与推荐的利益冲突；渠道价值未验证前商户不付费 短中期起：餐饮、美容、线下门店
按结果收费：成交抽佣 用户经 Iris 成交，商户或平台按单付费；Agent 渠道专属权益的归因 既有需求未必增量；联盟媒介限制（S02）须以直接合同绕开 短中期：餐饮、机酒；长期唯一模式
按结果收费：节省分成 用户看到的日元差额按比例收取 节省须可归因、可核验；与伙伴权益冲突 短中期：机酒取消重订

按结果收费与效果可度量互为条件：只有用户能看见前后对照的任务才能按结果定价，按结果定价又要求产品把差额算清并留痕（U04）。

伙伴材料把合作分为支付、零售服务、场景合作三层（P02）；每层须落到具体权益：可触达人群、品牌使用、商品／时段数据、执行与售后入口、资金流程与责任分工。引荐、Logo 展示或备忘录不足以支持收入预测。

6.2任务贡献

按所有发起任务核算，不只看成功订单：

任务贡献 = q × F − c − h × k − ℓ − p

q 为可收款比例（失败、取消、无法归因进分母），F 为每可收款任务净收入，c 为模型、工具、电话等变动成本，h × k 为人工分钟 × 人工单价，ℓ 为期望净异常损失，p 为分摊保障费用。

量级约束（假设算例，非费率）：q=70%、c=¥50、k=¥50/分钟时，F=¥300 的任务只允许约 3 分钟人工，F=¥1,000 允许约 13 分钟。电话通话成本远低于人工成本（D01），人工兜底才是主要变量。结论：主线必须以自动完成为目标，人工只做异常兜底；获客勾子不以此公式评价。异常可能成批发生，另列单日最大暴露与退款资金需求。

6.3市场规模

不做自上而下 TAM。METI 2024 年 BtoC 电商 26.1 万亿日元、餐饮服务 9,692 亿日元、旅行服务 3.5249 万亿日元（S01，官方）只说明产业基础。可得收入按下式自下而上计算：

年度可得收入 = 可触达人数 N × 激活率 a × 年任务数 t × q × F

量级算例：N=10,000、a=20%、t=6、q=60%、F=¥300 时年收入 ¥216 万；同条件下年收入 ¥1 亿需约 46 万可触达用户。伙伴确认能触达多少人，是首轮商务的数字交付物。跨境客群的分母是合作酒店与渠道能分发到的游客数，不是全部访日人数。

7取胜需要的能力

先说结论四项能力是主线的前提，缺一项主线就退化为推荐工具。

7.1执行层：通用能力底座与三条执行路径

通用 Agent 能力是底座：云端电脑可在任何品牌、商户、航司与 OTA 的官方站上按用户授权操作，AI 电话可联系任何只接电话的商户；两者让 P2 场景无需针对性投入即可完成（U05）。在此之上，执行按商户的真实库存位置选路：有结构化接口走 API 或台账系统，封闭平台走官方深链，电话长尾走 AI 电话；专用接入只为 P0、P1 场景建设。电话是日本特有的必要能力，技术方案已具备（D01），商户接受度与来电信任是待验证项。不绕开平台禁止自动化的规则。

7.2年龄与身份风险管理

产品必须掌握用户年龄；夜间娱乐、婚恋等 18 岁以上场景启用前做身份验证；跨境游客以护照信息判断。目的是把年龄相关的法律责任留在可控范围内，而不是留给事后处理（S41、S24、U03）。身份验证只用于门槛判断，不作画像。不做免登录：用户先以 Google、Apple 或 LINE 登录，出生日期在注册时采集（U22），这与 D03 的"价值先于账号"不同，以本文为准；年龄采集与身份验证的实现见 D04 的 A6。

7.3授权与责任

授权按"金额 × 可逆性 × 首次／重复"分层（P05）：首次高金额必须确认，连续同意后同类操作转自动；常设规则下的自动执行与限额内自动同等对待，首次须确认，只订可免费取消的，责任与损失预算规则同样适用（§5.1 原则 6）；多人任务不因发起人授权而获得其他人的资料。向商家透露信息分两档：本人基本信息（预约名、电话）随任务授权，审批卡上列明即可；他人信息与健康类信息（同行者忌口、过敏）首次向某商家透露前单独确认，只在当次任务内使用，写入记忆前另问（U26）。责任做成有限服务承诺＋统一受理＋损失预算：错订、重复下单、未执行取消由 Iris 承担合同责任；商户拒绝履约由 Iris 协调并按协议追偿；专业结果不纳入承诺。承诺范围与预算在对外宣传前落实，并进入 §6.2 的 ℓ 与 p；广泛风险保障须与保险主体确认是否构成保险业务（S37）。

7.4商户标准与金融分工

商户标准

  • AI-ready 是 Iris 的私有商户验收标识，覆盖主体与范围、数据与供给、用户授权、成交确认、变更退款、责任响应、数据治理、标识维护八项；不得让消费者误以为是政府或行业认证（S38）。
  • 获得第二家独立伙伴采用且实施成本下降后，再投资公共品牌。

支付

  • 原则：Iris 只做 agent，不经手任何资金：不收付用户的购物款、不垫钱、不持卡、不预收余额。额度、审批、日志与撤销由 Iris 管；钱由用户的支付方式直接付给商家，或由持牌机构处理（U24）。Iris 自己的订阅费按普通商户收款，与替用户付款无关。
  • 目标：agent 在额度内尽量自己完成购买，且不需要逐个商户接入（U10、U11）；做不到时把购买办到付款前一步，由用户一键完成。
  • 现在：能用用户在平台账户里已存的支付方式下单的，agent 直接下单；遇到发卡行验证或不能代付时交还用户，优先深链跳转商家页面，不支持时由用户接管云端浏览器付款，接管期间模型暂停、不截屏，云端浏览器按 PCI DSS 范围管理。StarPay 加盟店经 NETSTARS 的授权 SDK 付款：用户的卡信息只交给 NETSTARS，agent 经 API 发起，NETSTARS 付给加盟店（NETSTARS 内部调研中，U24）。
  • 第二步：找持牌伙伴做预付钱包加一次性卡。用户先充值或按固定规则自动充值，伙伴按任务发用户名下的一次性限额卡，agent 在额度内用卡付任何收卡的官方站。充值不能按每笔从用户的卡实时扣，那属于 Visa 禁止的 Card Fronting（Visa Core Rules 2026-04）。
  • 长期：卡组织 agent 令牌，资金从用户的卡直接付给商家（Mastercard Agent Pay 2026-05 已在日本完成首笔生产交易，未一般开放；Visa 在日本处于发卡行就绪测试，S46）；或 Stripe Link 进入日本后直接接入，Iris 的角色与 Muse 相同（目前仅限美国、加拿大账户，S47、S48）。两条路都不需要 Iris 经手资金，哪条先到先接哪条。
  • 不采用 Iris 名下虚拟卡、先付后收：Iris 要垫钱、收钱，违背不经手资金的原则（U24 取代 U11 中的这一做法）。
  • NETSTARS：不做钱包、没有发卡资质，与 Visa、Mastercard 的合作是长期方向；短期合作是授权 SDK 用于 StarPay 加盟店付款，以及 Iris 订阅费的收款；其资金移动业注册证明其自身能力，牌照不转移给 Iris（S35）。
  • 现阶段不做：需要商户逐一签约或接入的路线（结账协议、商户合同）是长期工程。
  • 合规：Iris 不经手资金，不涉及資金決済法的登记；代订机酒收取服务费是否触发旅行业法、云端浏览器接管的 PCI DSS 范围，由法律意见与审核机构确认。

A.2方法选型

先说结论方法的重量与证据量匹配。当前没有用户任务数据，因此采用七个有区分度的维度做定性判断，并逐格注明依据。

具体做法：用 JTBD 定义场景单元并按 MECE 组织（§3）；用七个维度先评 agent 做这件事的优劣势、再分层并标注来源（§4、A.3）；竞争分析聚焦替代品、买方、供应商三股有张力的力（§2.2）；市场规模只做自下而上的量级约束（§6.3）。用户频次、可服务规模与佣金率需要任务日志或合同才能量化，留待 90 天验证产出（§8）。

A.3评估维度

七个维度的定义、高低锚点与分层规则见表 4-1 与 §4.1，不在此重复。设计原则：先判断 agent 相对现成工具的优势（执行增量、频次与持续责任、上下文可得与积累、Iris 资产兑现）能否在该场景发挥，再看信任与收入（结果可核验、变现与商户关系），最后用可控与风险作门槛。三档序数，不加权求和；每格的依据与来源见表 4-2。
